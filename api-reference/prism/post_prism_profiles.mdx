---
title: "Batch public profiles"
openapi: "POST /prism/profiles"
---

Pass 1–50 objects in `items`, each with `platform`, `handle`, and optional `custom_id`. Results retain input order and caller IDs. Handles may be bare, begin with `@`, or be canonical HTTPS profile URLs. URLs must match the selected platform; redirects, credentials, query strings and fragments are rejected.

**Supported platforms:** Instagram, TikTok, YouTube, Twitter, Threads, Twitch, Snapchat, Truth Social, Bluesky, Kwai, LinkedIn and Facebook. Social profiles use [ScrapeCreators](https://docs.scrapecreators.com/), YouTube uses its [official API](https://developers.google.com/youtube/v3/docs/channels/list), Bluesky uses its [public API](https://docs.bsky.app/docs/api/app-bsky-actor-get-profile), and LinkedIn uses [ScrapeBadger](https://docs.scrapebadger.com/). Other platform values return `unsupported`, with no final charge.

Truth Social is limited to prominent publicly accessible accounts. Facebook gated pages are rejected. LinkedIn's `id` is the returned public profile slug (`ext.id_kind: public_id`), not a numeric member ID. Twitch partnership and Twitter blue-verification flags remain separate from canonical verification. Kwai counts reflect the public source even when surprisingly small; no values are inferred. Truth Social's HTML biography remains in `ext.bio_html`, with canonical `bio` null. Provider access and available allowance determine whether a live lookup succeeds.

Posts, `since` and per-item `stop_at_id` remain unsupported and reject before spending. Typed per-item SSE is implemented locally behind `streamEnabled: false`; requesting SSE currently returns 503 before reservation pending combined verification. The JSON-serialized `items` array must fit the 16,000-character parameter limit.

Every `ok` row contains a canonical Author in `data`. The returned identity must match the input. Unknown follower, verification or location fields remain null; hidden YouTube subscriber counts remain null. Provider errors are not treated as nonexistent accounts. A definitive source miss returns `not_found`.

The request holds one credit per input, or five for a LinkedIn input, then refunds every `not_found`, `unsupported`, `error` and `deferred` row. Each successful profile costs one credit, or five for LinkedIn. Repeated input rows are separate lookups. Include the summed hold in `X-Max-Credits`.

At most four source calls run concurrently. Each item shares a twelve-second deadline across allowance reservation, fetch, body read and parsing, within a common forty-second deadline. Source JSON bodies are bounded to 1 MiB and normalized successful rows to 64 KiB. Oversized or invalid rows are errors with zero final charge. No new source work starts after twenty-eight seconds. Rows left unstarted return `deferred` and cost zero. A provider authentication or quota failure stops new calls to that provider while other providers continue. The response is never cached. For JSON, replay the same `Idempotency-Key` for zero-cost replay, or retry only failed/deferred rows with a new key.

Both JSON and successful streamed executions now use `summary` with exactly nine fields: `total`, `ok`, `not_found`, `unsupported`, `error`, `deferred`, `coverage`, `credits_charged` and `credits_refunded`. Coverage is successful rows divided by total rows. Live charged credits equal the settled envelope charge; refunds are the original hold minus that charge. Existing JSON row and pagination fields remain. The source summary is validated again by canonical billing and the API settlement path. A successful JSON replay reports zero new `credits_charged` and `credits_refunded` in `data.summary`, while top-level `original_summary` preserves the original settled summary. Rows retain their original prices; the current replay envelope costs zero.

Once enabled, `Accept: text/event-stream` emits provisional `result` chunks shaped as `{type: "result", key: "profile", value: {provisional: true, index, row}}`, then exactly one `done` chunk shaped as `{type: "done", summary}` after durable settlement. There are no `start`, `item` or `complete` frames in this batch mode. Input indexes identify concurrent completion-order rows. Provisional row credits do not certify final billing. Failure attempts refund before `{type: "error", code, message}` followed by `{type: "done", summary}`; confirmed full refunds report all-request error counts and zero charged credits. If settlement/refund cannot be confirmed, charged and refunded credits are both unknown (`null`). Disconnect suppresses output and prevents new source dispatch; bounded in-flight work still finishes and settles.

Each SSE message contains exactly one `data: <JSON>` line followed by a blank line. There are no named `event:` fields. Parse `event.data` as JSON and switch on `chunk.type` (`result`, `error` or `done`); the `type` discriminator is part of every chunk, including snapshot replays. Network reads can split a message or Unicode character, so decode UTF-8 incrementally and buffer until the blank-line boundary.

A nonempty `Idempotency-Key` (up to 256 characters) is scoped to the account and API key for 24 hours. Same-body JSON and, once enabled, SSE requests share one claim and canonical JSON snapshot, bounded to 4 MiB. A completed snapshot replays without another provider call, credit hold or ledger mutation. Stream replays emit the saved rows in input order with `provisional: false`, then `done` with zero new charged/refunded credits. `Idempotent-Replayed: true`, `X-Idempotent-Replay: true` and `X-Original-Request-Id` identify replays. Valid stored failures emit `error`/`done` with zero new charge/refund; preflight failures with invalid inputs keep their original JSON status even if SSE is requested. A changed body returns 409 `IDEMPOTENCY_CONFLICT`; pending claims return 409 `REQUEST_IN_PROGRESS`. Retry failed/deferred inputs with a new key.

A live stream settles billing before saving its JSON snapshot, including after disconnect. It attempts storage once, waiting up to three seconds; storage uncertainty does not reverse settled billing or release the claim for an immediate duplicate request. If storage committed but acknowledgment was lost, a later request can replay; otherwise the claim stays pending until its original expiry. Finished snapshots cannot be overwritten, and expired/replaced claim tokens cannot save late results. An unconfirmed refund does not save a fabricated settled outcome. The staged YouTube transcript batch also supports this replay mechanism, with an 8-MiB caption snapshot bound. The staged comment-lookup batch shares this mechanism with a 4-MiB snapshot bound, key=item, and zero current aggregate credits_used on replay. Other streams retain their existing idempotency restrictions.

The data-only chunk framing, JSON type labels, per-endpoint key and nine-field live summary align with the [reference batch documentation](https://www.socialcrawl.dev/docs/batch). The local indexed `row` wrapper and JSON `items` envelope still differ; exact row/field compatibility and reference deadlines remain gaps. Both batch stream gates remain false. Saved/native projection and synthetic stream/settlement tests plus disposable PostgreSQL claim checks do not certify deployed streams, broader provider contracts or a real billing-ledger transaction.

For MCP use `execute_endpoint`. The Python skill requires `--allow-mutation`, the batch budget and an idempotency key. Both clients calculate the complete hold before sending the batch.
