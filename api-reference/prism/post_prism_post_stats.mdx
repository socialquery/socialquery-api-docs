---
title: "Batch public post statistics"
openapi: "POST /prism/post-stats"
---

Pass 1–100 post links in `urls`. Rows retain the original URL and input order. Supported platforms are YouTube, Bluesky, Instagram, TikTok and LinkedIn. Other hosts return an unbilled `unsupported` row. A recognized platform with an invalid post path returns an unbilled `error`. The serialized array must fit 16,000 characters.

Each successful row contains `engagement` with nullable `views`, `likes`, `comments`, `shares`, `saves` and `reposts`, plus a server `fetched_at` timestamp. Optional `include` is a CSV subset of `views,likes,comments,shares,saves,reposts`; omitted include returns all six. Whitespace is trimmed and duplicates are collapsed into canonical metric order. Empty or unknown names reject before hold. Selection adds no requests and does not alter the price. Even if all selected counts are unavailable, a validated successful source row keeps null values and its usual charge. Missing metrics remain null. Bluesky reposts are not relabeled as shares. Instagram save/repost counts appear only if the source returns them; `include=saves` selects an existing normalized count; it does not request additional source enrichment or unlock a missing save count. Counts are public provider observations, not complete private analytics. LinkedIn accepts canonical `/posts/...-activity-...` links; feed URNs and shortened redirects are not supported. Instagram accepts both `/p/code/` and `/<handle>/p/code/` permalinks, as well as reels.

The hold is one credit per URL, two for Instagram and five for LinkedIn. Every successful row costs that tier; `not_found`, `error`, `unsupported` and `deferred` rows cost zero. No result is charged unless the source identity matches and at least one valid engagement count is available before output selection. The settlement check verifies the selected keys/count types, original URL, platform, status, price and fetched timestamp. Only a definitive empty YouTube or Bluesky post result becomes `not_found`; other source failures stay `error`.

Four workers share a common forty-second source budget. Every item has one twelve-second deadline across allowance reservation, identity resolution, fetch, body and parsing, with no new source step started after twenty-eight seconds. Each JSON source body is bounded to 1 MiB. An allowance or identity resolution finishing after disconnect or dispatch-window expiry cannot start another request. Unstarted rows are deferred and refunded. A provider quota/authentication failure stops new requests to that provider. There is no SocialQuery response caching. Source freshness is provider-dependent. For JSON, use an `Idempotency-Key` for free replay; retry failed/deferred rows with a new key. Typed per-item SSE is staged locally behind `streamEnabled: false`; requesting it currently returns 503 before reservation pending combined verification.

Both JSON and successful streamed executions now use `summary` with exactly nine fields: `total`, `ok`, `not_found`, `unsupported`, `error`, `deferred`, `coverage`, `credits_charged` and `credits_refunded`. Coverage is successful rows divided by total rows. Live charged credits equal the settled envelope charge; refunds are the original hold minus that charge. Existing JSON row and pagination fields remain. The source summary is validated again by canonical billing and the API settlement path. A successful JSON replay reports zero new `credits_charged` and `credits_refunded` in `data.summary`, while top-level `original_summary` preserves the original settled summary. Rows retain their original prices; the current replay envelope costs zero.

Once enabled, `Accept: text/event-stream` emits provisional `result` chunks shaped as `{type: "result", key: "stat", value: {provisional: true, index, row}}`, then exactly one `done` chunk shaped as `{type: "done", summary}` after durable settlement. There are no `start`, `item` or `complete` frames in this batch mode. Input indexes identify concurrent completion-order rows. Provisional row credits do not certify final billing. Failure attempts refund before `{type: "error", code, message}` followed by `{type: "done", summary}`; confirmed full refunds report all-request error counts and zero charged credits. If settlement/refund cannot be confirmed, charged and refunded credits are both unknown (`null`). Disconnect suppresses output and prevents new source dispatch; bounded in-flight work still finishes and settles.

Each SSE message contains exactly one `data: <JSON>` line followed by a blank line. There are no named `event:` fields. Parse `event.data` as JSON and switch on `chunk.type` (`result`, `error` or `done`); the `type` discriminator is part of every chunk, including snapshot replays. Network reads can split a message or Unicode character, so decode UTF-8 incrementally and buffer until the blank-line boundary.

A nonempty `Idempotency-Key` (up to 256 characters) is scoped to the account and API key for 24 hours. Same-body JSON and, once enabled, SSE requests share one claim and canonical JSON snapshot, bounded to 4 MiB. A completed snapshot replays without another provider call, credit hold or ledger mutation. Stream replays emit the saved rows in input order with `provisional: false`, then `done` with zero new charged/refunded credits. `Idempotent-Replayed: true`, `X-Idempotent-Replay: true` and `X-Original-Request-Id` identify replays. Valid stored failures emit `error`/`done` with zero new charge/refund; preflight failures with invalid inputs keep their original JSON status even if SSE is requested. A changed body returns 409 `IDEMPOTENCY_CONFLICT`; pending claims return 409 `REQUEST_IN_PROGRESS`. Retry failed/deferred inputs with a new key.

A live stream settles billing before saving its JSON snapshot, including after disconnect. It attempts storage once, waiting up to three seconds; storage uncertainty does not reverse settled billing or release the claim for an immediate duplicate request. If storage committed but acknowledgment was lost, a later request can replay; otherwise the claim stays pending until its original expiry. Finished snapshots cannot be overwritten, and expired/replaced claim tokens cannot save late results. An unconfirmed refund does not save a fabricated settled outcome. The staged YouTube transcript batch also supports this replay mechanism, with an 8-MiB caption snapshot bound. The staged comment-lookup batch shares this mechanism with a 4-MiB snapshot bound, key=item, and zero current aggregate credits_used on replay. Other streams retain their existing idempotency restrictions.

The data-only chunk framing, JSON type labels, per-endpoint key and nine-field live summary align with the [reference batch documentation](https://www.socialcrawl.dev/docs/batch). The local indexed `row` wrapper and JSON `items` envelope still differ; exact row/field compatibility and reference deadlines remain gaps. Both batch stream gates remain false. Saved/native projection and synthetic stream/settlement tests plus disposable PostgreSQL claim checks do not certify deployed streams, broader provider contracts or a real billing-ledger transaction.

Sources: [YouTube Data API](https://developers.google.com/youtube/v3/docs/videos/list), [Bluesky](https://docs.bsky.app/docs/api/app-bsky-feed-get-posts), [ScrapeCreators](https://docs.scrapecreators.com/), and [ScrapeBadger](https://docs.scrapebadger.com/). Their available allowance determines live availability. MCP `execute_endpoint` and the Python skill calculate the full URL-based hold before calling; the Python skill also requires `--allow-mutation` and an idempotency key.
