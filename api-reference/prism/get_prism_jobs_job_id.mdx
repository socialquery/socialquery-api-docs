Durable API-key-owned profile and post-stat batches use existing provider adapters and allowances. No production readiness is claimed. Read status and up to five contiguous completed chunks (250 rows). Each result preserves its submitted custom_id and global index. Pass next_cursor to continue; when null and results_complete=false, poll again with the same cursor. Queued rows have no results yet. Interrupted, expired or key-disabled chunks become deferred at zero charge; resubmit deliberately. Results expire seven days after submission. Unsupported options and exhausted upstream allowances are separate from implementation status.

The nine summary fields are `total`, `succeeded`, `not_found`, `errors`, `unsupported`, `deferred`, `credits_used`, `processed`, and `remaining`. These are local contract names; exact upstream parity has not been certified.

The REST body limit is 3 MiB. MCP additionally enforces its existing 16,000-character per-parameter limit; split large item arrays or use REST/Python. No client automatically polls or resubmits deferred rows.

Each response reads status, credit totals, progress and results from one read-only repeatable-read database snapshot, so concurrent worker settlement cannot mix versions. Polling costs zero and never executes a provider or changes the credit ledger.

The read contract is verified locally against the authenticated API, disposable PostgreSQL, both MCP clients and Python. Reads have independent gates and are enabled without submission or worker activation. Unsupported submission options remain tracked on POST. ## Completion callbacks

On submission, optionally include `"webhook": {"url": "https://hooks.example.com/events"}`. Only the URL field is accepted. The URL must be an ASCII HTTPS DNS name, without credentials, an explicit port or fragment, and fit 2,048 characters. URL validation runs before the reservation; submission does not perform DNS or HTTP work. The destination is immutable and participates in idempotency fingerprints. Exact replays keep the original job and do not create another callback.

The initial successful `202` returns `data.webhook_secret` once. Save that value securely. Replays, list/detail reads and callback bodies omit it. A lost initial response cannot recover the secret through replay; poll the job instead. The server retains the secret in a server-only table until a delivery claim or suppression, then erases it. Pending callback records follow the existing seven-day job retention.

After every chunk settles and the job has no held credits, a worker can claim one terminal-summary callback. Its `PrismJobCompletionEvent` payload contains a schema version, stable event ID, completed/failed event type, terminal time, job metadata, settled summary and relative results URL. Results, source prose, contact fields, creating-key identifiers, callback URL and secret are omitted. Read results with the creating API key. A completed job may contain failed, unsupported, missing or deferred rows; inspect its summary rather than treating completion as all-row success. Successful and failed jobs can emit events; callback outcome never changes their settled credits and adds no customer charge.

Verify `X-SocialQuery-Signature` as `v1=` followed by the lowercase hex HMAC-SHA256 of `X-SocialQuery-Timestamp + "." + raw_body`, using the **whole returned secret string as the UTF-8 key**. Verify the exact body bytes with a constant-time comparison, reject stale timestamps using a short receiver-defined tolerance (for example five minutes), and deduplicate `X-SocialQuery-Event-Id`. The timestamp is seconds since the Unix epoch. The body and header event IDs agree.

The worker rechecks the creating key's active state and jobs/child scopes when claiming delivery. Revocation, expiry, removed scopes or expired jobs suppress it. DNS is checked at delivery, and every answer must be public; private, reserved, mixed-public/private and unsupported address forms reject. The HTTPS connection uses one validated pinned address while verifying the original hostname certificate. It sends no API key, authorization cookie or signing secret. It follows no redirect, reuses no connection and reads no receiver body; only response status headers are used.

Delivery has one attempt with a ten-second DNS/HTTPS deadline, inside a twenty-second claim/delivery/recording budget. A callback tick performs no child-provider work. Late DNS or claim completion cannot start a new HTTP request. Every non-2xx status, including redirects and rate limits, is terminal. Timeouts, network uncertainty, lost acknowledgments or a crashed worker are never retried automatically; a consumed claim cannot be sent again. This is **at most one attempt**, not a guarantee that the receiver processes an event exactly once. Polling remains available.

`webhook_delivery` is null for jobs without callbacks. Otherwise key-owned submission/read views expose `status` (`pending`, `sending`, `delivered`, `failed`, `unknown`, `suppressed`), `attempted_at`, `finished_at`, `http_status` and a bounded outcome code. These expose no URL or secret. `attempted_at` records claim/processing time, including suppressed callbacks. A `sending` claim abandoned for more than one minute becomes `unknown / worker_interrupted`, with no redispatch; late updates are fenced.
